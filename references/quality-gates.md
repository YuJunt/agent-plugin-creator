# 专业插件质量门禁

一个插件只有同时通过以下门禁，才能被描述为“可交付候选版本”。静态结构通过只说明包形状正确，不说明业务行为正确。

| 门禁 | 必须回答的问题 | 证据 |
| --- | --- | --- |
| 业务契约 | 插件解决谁的什么业务问题？输入、输出、权限和失败边界是什么？ | `README.md` 或交付报告中的业务契约 |
| Skill 质量 | Skill 是否有准确触发描述、明确步骤、结构化输出和反幻觉边界？ | `SKILL.md`、2–3 个触发用例、with-skill/baseline 结果 |
| MCP 质量 | 每个工具是否有窄边界、清晰 schema、可操作错误、分页/限制和读写标识？ | server 代码、工具清单、Inspector 或 client 调用结果 |
| 运行时 | server 能否在目标运行时启动，客户端能否初始化、列工具、调用代表性工具？ | 运行日志、SDK 版本、启动命令 |
| 数据与权限 | 是否最小权限、无秘密入包、认证责任明确、写操作需确认？ | 权限矩阵、秘密扫描、认证说明 |
| 评估 | 是否有稳定、独立、只读且可验证的问题；结果是否可复现？ | Skill evals、MCP 10 问题集、答案或断言 |
| 兼容性 | 目标客户端支持哪些 transport、扩展和认证能力？ | 客户端矩阵与冒烟测试 |
| 发布 | 是否有版本、许可证、变更说明、回滚和人工发布步骤？ | manifest、LICENSE、CHANGELOG 或发布报告 |

## 失败处理

任何门禁失败都必须在交付报告中标记为 `blocked`、`warning` 或 `passed`。不得用“规范验证通过”覆盖运行时或业务评估失败。若 MCP server 未真实启动，交付物只能称为“结构样例”或“实现草稿”，不能称为生产就绪。

## 运行时兼容矩阵

对每个 MCP server 记录语言、SDK 版本、transport、启动 command、工作目录、环境变量、认证方式、目标客户端和测试结果。若官方示例依赖某个 SDK API，必须在 `requirements.txt` 或 `package.json` 中固定兼容范围，并重新运行启动测试。

## 证据化业务输出

业务插件的 Skill 应要求模型区分四种内容：原始事实、计算结果、风险解释和建议动作。所有重要结论都应保留实体 ID、来源字段或工具调用证据。对于数据不可用、权限不足、过期或矛盾的情况，应报告限制而不是推测。
